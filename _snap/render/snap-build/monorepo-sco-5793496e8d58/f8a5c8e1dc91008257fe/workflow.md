## READY FOR DEVELOPMENT STANDARD

A specification is "Ready for Development" when:

- **Actionable**: Every task has a file path and specific action.
- **Logical**: Tasks ordered by dependency.
- **Testable**: All ACs use Given/When/Then.
- **Complete**: No placeholders or TBDs.
- **Sufficient**: No known requirement, acceptance, dependency, or implementation gaps remain unresolved.
- **Coherent**: No unresolved ambiguities or internal contradictions.

## SCOPE STANDARD

A specification should target a **single user-facing goal** within **900–1600 tokens**:

- **Single goal**: One cohesive feature, even if it spans multiple layers/files. Multi-goal means >=2 **top-level independent shippable deliverables** — each could be reviewed, tested, and merged as a separate PR without breaking the others. Never count surface verbs, "and" conjunctions, or noun phrases. Never split cross-layer implementation details inside one user goal.
  - Split: "add dark mode toggle AND refactor auth to JWT AND build admin dashboard"
  - Don't split: "add validation and display errors" / "support drag-and-drop AND paste AND retry"
- **900–1600 tokens**: Optimal range for LLM consumption. Below 900 risks ambiguity; above 1600 risks context-rot in implementation agents.
- **Neither limit is a gate.** Both are proposals with user override.

## WORK PACKET (SLICE) STANDARD

When Build is aimed at more than one unit of work — an epic with a list of stories, a batch of stories passed by hand, or an open-ended "find what to build next" with no input — the first job is to decide **how much to build in this pass**. Individual stories are frequently too granular to build and ship on their own, and epics are frequently too big to build in one pass. The unit this workflow actually implements is a **work packet** (a "slice"): the chunk a competent developer would build on one branch, and hand off to be deployed and tested as one increment.

A work packet is:

- **Logical** — one coherent part of a feature, or a whole feature when it is small enough. Its parts belong together; splitting them would produce a change that only makes sense once a later change lands.
- **Reviewable** — a reviewer can hold the entire change in their head in one sitting. A diff too large to review as a unit means the packet is too big.
- **Testable** — it can be verified as a unit once complete, without waiting on work outside it.
- **Deployable** — it can merge and ship on its own, leaving `main` in a working, releasable state even if nothing after it is ever built.

Forming a packet:

- **Group** stories that share a behavior slice, a surface, or a data-model change and that a developer would naturally implement together on one branch. A single story is a valid packet when it already meets all four criteria alone.
- **Take the whole epic as one packet** when the epic is a single small feature a developer would build and PR together — do not force an artificial split just because the epic lists several stories.
- **Carve a narrower slice** when the epic is large: pick the smallest packet that still ships something meaningful and defer the rest for later passes. When in doubt, carve narrower.
- **Exclude** a story from the packet when it is independently shippable and pulling it in would make the change too large to review or test as one unit.

This standard decides *which stories enter this build pass*. The SCOPE and token standards above still apply to the resulting spec; a well-formed packet that genuinely cannot be specified within them is a signal it is really two packets. A multi-story packet that a developer would still PR together is a legitimate reason to accept a spec above the soft token limit.

## LAKE WRITE-BACK STANDARD

When a SnapCT context lake exists, a build leaves the lake truer than it found it. After step-04 review passes and before step-05 present, step-04b edits the lines of the owning feature page that this change touched, and nothing else:

- It writes only to `features/` pages (and the feature map when a page is created). Structure pages (`api/`, `modules/`, `data-model/`, `architecture/`) are generated by SnapCT and never touched here.
- It marks each line it writes `verified: <HEAD> by snap-build (<spec slug>)` and resets `confirmed` to `needs-confirmation` for rule, validation and state changes. A person confirms later through SnapCT.
- It takes new IDs from SnapCT's `ids.py` and halts when SnapCT is not installed. It never invents one.
- The page edit belongs to the same branch and PR as the code.
- No lake, or no behaviour change, means the step writes nothing.

## WORKFLOW ARCHITECTURE

This uses **step-file architecture** for disciplined execution:

- **Micro-file Design**: Each step is self-contained and followed exactly
- **Just-In-Time Loading**: Only load the current step file
- **Sequential Enforcement**: Complete steps in order, no skipping
- **State Tracking**: Persist progress via spec frontmatter and in-memory variables
- **Append-Only Building**: Build artifacts incrementally
