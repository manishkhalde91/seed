# Step 4b: Write Back to the Context Lake

## RULES

- **Language** — Speak in `English`. Write any file output in `English`.
- This step runs once, after step-04 review has passed and before step-05 present. It is the only place Snap writes to the context lake.
- Edit **feature pages only** (`features/{slug}.md`, or `features/{slug}/index.md` and its parts), plus the feature map row in `prd/index.md` when a page is created. Never touch `api/`, `modules/`, `data-model/`, `architecture/`, `blast-radius-map.json`, `lake.yaml` or `product-rules.md`. Those are generated by SnapCT on refresh.
- Write what the system does **after this change**, as the code now does it. Do not describe intent, plans or defects.
- Never invent an ID, a `source:` path or a line number. IDs come from `ids.py`; sources come from code you have just opened.
- Do not commit here. The page edit rides in the same change set as the code; step-05 commits both.
- Do not set `confirmed:` to a person's name. Only SnapCT's resolve step does that.

## INSTRUCTIONS

### 1. Gate

1. Run `uv run {project-root}/_snap/scripts/resolve_artifacts.py --project-root {project-root} --profile overview` and read the JSON.
   - `files` empty (no lake) → skip this whole step silently and go to NEXT. Say nothing about a lake.
   - `contract` is `legacy` (the lake has no `lake.yaml`, so it predates the current layout) → write nothing, and set `lake_writeback` to one soft line for step-05: "Lake write-back skipped: the context lake predates the current layout. Run `snapct migrate` when convenient." Go to NEXT. Never create or edit pages in a lake that has not been migrated, and never HALT for this.
2. Read `{spec_file}` frontmatter: `feature` and `rules_touched`. If `feature` is empty or missing (the lake exists and is current, so the overview above found files), HALT and ask the human for the feature slug (offer the slugs under `<lake>/features/`, or a new one). Record it in `{spec_file}` and continue.
3. Run `uv run {project-root}/_snap/scripts/resolve_artifacts.py --project-root {project-root} --profile feature=<feature>`. Take `lake` from the JSON. Set `{lake}` to it and `{workspace_root}` to the folder two levels above it (the lake is `<workspace root>/_snap-output/context`).
4. Set `{head}` to the full commit hash of the current HEAD from version control (`NO_VCS` if there is none). Set `{slug}` to `{spec_file}`'s file name without `.md` (for example `spec-partial-refunds`). Set `{today}` to the current date.
5. Read the diff of this change: `{diff_file}` if it exists, otherwise a unified diff of all changes since `{baseline_commit}`. Read the frozen intent in `{spec_file}`. You need both.

### 2. Find what the change did to the lake

Read the feature page. Build four lists from the diff, the frozen intent and `rules_touched`; open the code for every one, because the page and the spec can be wrong about it:

- **Changed** — a rule, validation, scenario or state line already on the page whose behaviour this change altered.
- **Removed** — a line whose behaviour this change deleted.
- **New** — behaviour the change adds that no line covers (a new rule, validation, scenario, state change, or capability).
- **Echoes** — requirement text elsewhere on the page that repeats a changed value (an FR consequence, a journey step, a scenario). Search the page for the old value, not just for the ID.

A rule listed in `rules_touched` that lives in `product-rules.md` (shared across features) is **not edited here**. Append one entry to `/Users/manish.khalde/Desktop/seed/monorepo-sco/_snap-output/implementation-artifacts/deferred-work.md` (`source_spec: {spec_file}`, summary: "Shared rule <ID> was changed by this build; update product-rules.md through SnapCT", evidence: the diff hunk) and tell the human in step-05.

If all four lists are empty (a refactor with no behaviour change), write nothing and go to NEXT.

### 3. Edit the page (page exists)

Edit in place, smallest change that makes the page true. Keep the line format: an ID, one sentence, then `feature`, `source`, `verified`, `confirmed`.

- **Changed line** — update the sentence. Update `source:` to the new `path:line` if the code moved or changed lines. Set `verified: {head} by snap-build ({slug})`. For `BR-`, `VAL-` and `ST-` lines, set `confirmed: needs-confirmation` (the rule changed, so any earlier confirmation no longer holds). For `SC-` lines, leave `confirmed` as it is unless the expected behaviour changed, then reset it the same way.
- **Echo** — update the text to match. Leave its IDs alone.
- **Removed line** — delete it from its section and add it under `## Retired` as `- <ID> <sentence> — retired by {slug}, {today}`. Never reuse or renumber the ID.
- **New line** — allocate IDs first (below), then add the line to the right section (5 rules, 6 validations, 7 and 9 scenarios, 8 states, 10 integrations) with all four fields: `feature: <slug>`, `source: <path:line from the code you opened>`, `verified: {head} by snap-build ({slug})`, `confirmed: needs-confirmation`.
  - Every new `BR-` or `VAL-` must be named in the `Rules:` line of at least one FR in section 4. Add it to the FR it supports, or add a new `#### FR-N:` in the page's FR shape if the change is a new capability.
- If the page has an `status: proposed` header, leave it. Do not change `source_commit` or `timestamp` — refresh owns those.

**Allocating IDs.** Never type a number. Run, once per prefix you need:

```text
python3 {workspace_root}/snapct/tools/ids.py allocate <PREFIX> --count <N> --lake {lake}
```

Write each line straight after allocating. If `{workspace_root}/snapct/tools/ids.py` does not exist (SnapCT is not installed beside the lake) and you need at least one new ID, HALT with this message and do nothing else: "This change needs a new lake ID but SnapCT is not installed at `{workspace_root}/snapct`. Install SnapCT, or allocate the ID by hand and tell me what it is." Never write an ID you made up. A change that needs no new IDs does not need SnapCT.

### 4. Create the page (no page for this feature)

The feature is new to the lake. Create `{lake}/features/<feature>.md` from `{workspace_root}/snapct/templates/feature.template.md` (halt with the same SnapCT message if the template is missing). Fill only what the spec and the code you have opened support:

- Frontmatter: `type: Feature`, `title`, `slug`, `status: proposed`, `source_commit: {head}`, `timestamp: {today}`, `owner: "[not stated]"`.
- Section 1 (purpose and scope), 4 (each capability as `#### FR-N:` with testable consequences and a `Rules:` line), 5, 6, 7 (rules, validations, scenarios) and 11 (entry points and modules this change added or touched, plain text if no endpoint page exists).
- Sections 2, 3, 8, 9, 10 and 12: write `None recorded.` Do not invent personas or journeys. Add a `Q-` open question (IDs from `ids.py`) saying no product journey has been recorded for this feature yet.
- Allocate every FR, BR, VAL, SC and Q ID with `ids.py`. Lines get the four fields as above, `verified: {head} by snap-build ({slug})`, `confirmed: needs-confirmation`.
- Delete the template's instruction comments.

Then add the feature to the feature map table in `{lake}/prd/index.md`: one row (Feature, Slug, Owner `[not stated]`, Entry points, Detail link) with `(unconfirmed)` after the feature name. Do not edit other rows or the "Feature map confirmed on" line.

### 5. Check

If `{workspace_root}/snapct/tools/check_lake.py` exists, run:

```text
python3 {workspace_root}/snapct/tools/check_lake.py --output-dir {lake} --quiet
python3 {workspace_root}/snapct/tools/ids.py verify --lake {lake}
```

Fix only findings your own edits caused (a missing field, a duplicate ID, a new rule no FR names). Pre-existing warnings are not yours; do not touch them. If SnapCT is not installed, skip the checks and say so in step-05.

### 6. Record

Add one line to `{spec_file}`'s `## Spec Change Log` (or, if it has none, under Design Notes): "Lake write-back: <feature>, changed <IDs>, retired <IDs>, new <IDs>, deferred <IDs>". Keep a short list, `lake_writeback`, of those same facts for the step-05 summary.

If the lake lives outside this repository (a multi-repo system), the page edit will not be in this repo's commit. Say so in step-05 and name the lake path, so the human commits it in the lake's own repository on the matching branch.
